# Часть A. Плохой пайплайн

## Что делали

Написали сознательно плохой workflow для GitHub Actions. В нём 6 bad practices, каждая помечена комментарием `# BAD: ...`. Цель - показать на реальном прогоне, чем плохо так делать, и сравнить с хорошим пайплайном из части B.

Файл лежит в двух местах:
- `.github/workflows/bad-pipeline.yml` - рабочая копия, её запускает GitHub Actions (из другой папки он workflow не подхватит);
- `lab3-cicd/A-bad-pipeline/bad-pipeline.yml` - копия для отчёта.

Запускается только при изменении самого файла в ветке `lab3-cicd` или вручную через **Run workflow**, чтобы не мешать остальным пайплайнам команды.

## Стадии

| Job      | Что делает                                                                 |
| -------- | -------------------------------------------------------------------------- |
| `test`   | ставит зависимости, печатает конфиг, запускает «тесты» (шаг специально падает) |
| `build`  | `docker build -t app:latest`                                               |
| `deploy` | имитация деплоя через `echo`, запускается при любом исходе                 |

## Bad practices

1. **`actions/checkout@main`**. Версия экшена не зафиксирована, указана плавающая ветка. Любой коммит в репозиторий экшена может сломать или скомпрометировать пайплайн без изменений с нашей стороны. Хорошо: `@v4`, в идеале SHA коммита.
2. **Пароль в yaml** (`DB_PASSWORD: supersecret123`) и `echo` пароля в лог. Секрет попадает в историю git и в логи прогонов. Хорошо: `${{ secrets.DB_PASSWORD }}`, GitHub маскирует значение в логах.
3. **Нет кеша**. Ни `pip` (нет `cache: "pip"`), ни слоёв Docker (нет `cache-from` / `cache-to`). Каждый прогон качает и собирает всё с нуля.
4. **Нет сканирования образа** (Trivy). Образ с CRITICAL CVE беспрепятственно проходит дальше. Хорошо: `trivy-action` с `exit-code: '1'`.
5. **Тег `app:latest`**. Плывущий тег: не понять, какой коммит внутри, нельзя откатиться. Хорошо: тег с SHA коммита.
6. **`if: always()` на деплое**. Деплой идёт даже при упавших тестах, сломанный код уезжает на сервер. Хорошо: `if: success()`.

## Что видно на прогоне

- `test` красный (шаг `Run tests` упал), но `deploy` всё равно выполнился.
- В логах шагов `Print config` и `Deploy` пароль виден открытым текстом.
- Шаг установки зависимостей и сборка образа занимают полное время при каждом запуске (кеша нет).
